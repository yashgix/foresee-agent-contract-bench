Foresee gives AI assistants rich, structured car insurance estimates. The assistant then turns them into a few sentences for a person. I built a tool that measures what survives that step, and checks that Foresee's agent-facing documents stay consistent with each other.

The question

What survives between the quote and the person?

An assistant has to make a detailed quote easy to understand without dropping the facts that change the decision. Foresee's instructions already say what those are. The question is how reliably assistants follow them, and how much the instructions help.

How it works

Two checks, both offline

1 · Replay and grade

{{scenarios}} consumer questions about Foresee's {{published_results}} published example results ({{published_scenarios}} unchanged, {{variant_scenarios}} with a clearly labelled fictional carrier added). Each is answered by Claude Haiku and Sonnet under 4 setups: no instructions, Foresee's tool description, and each published version of its skill. Deterministic rules taken from Foresee's own guidance grade every reply.

2 · Contract checks

The tool compares Foresee's live MCP schema, docs and skills with each other, so an inconsistency is caught automatically. Renaming one field in the schema makes the check fail; updating the docs makes it pass again.

How it's checked

Recorded replies are re-scored without any model calls, and the grader's verdicts were compared with hand labels. The runner uses a subscription with every tool off and refuses API keys. {{tests}} tests; three Codex reviews, all NO-GO, with their findings fixed.

Technical details

Method, data, results and limits

Everything here is reproducible from the repository: make snapshot fetches Foresee's public documents and checks them against pinned hashes, make check runs the tests, and make score re-scores the {{replies}} recorded replies without a model call.

Data and provenance

EvidenceCountWhat it is
Live Foresee quotes0Not collected. Foresee's terms allow quotes only with your own information, on behalf of a person actually shopping, and don't allow republishing quote data. Test profiles or the author's details would not meet that, so live testing waits for Foresee's permission.
Published Foresee results{{published_results}}The auto, home, renters and auto + renters examples in Foresee's public docs: real outputs Foresee published, not insurer-confirmed prices.
Scenarios on unchanged published results{{published_scenarios}}Different consumer questions about the same published results.
Scenarios with a synthetic change{{variant_scenarios}}A published result plus one labelled change: fictional carriers (priced ones marked "(synthetic)"), a state note, or a different coverage ask with the real carriers removed. No invented price is attributed to a real carrier.
Recorded replies{{replies}}{{scenarios}} scenarios × 4 setups × 3 replies (Haiku twice, Sonnet once). Repeats of one result are not extra data diversity.
Checks scored{{checks}}Each scenario applies only the rules relevant to it ({{categories}} scenario categories).

Tested against the live system: one standard MCP handshake (initialize and tools/list) to read the schema, and public document fetches. Not tested: live quotes, carrier confirmations, latency, load or security.

Setups and rules

The same prompt is sent four ways: no instructions (no Foresee text, a bare baseline), tool description (Foresee's server instructions and tool description, as every MCP client receives them), and with each published copy of the quote-insurance 0.8.6 skill: the website copy and the repository copy, which differ by 35 lines. The tool result is given as text in the prompt, rebuilt from the published dense text and validated against Foresee's live output schema.

RuleForesee guidance it encodes
numbers_supported"State only numbers the result contains — never interpolate." A $ figure written as a price (with cents, or per month, 6 months or year) must match a price, range bound, single ladder step, coverage cost, spread or multi-line total, for the named carrier and stated period. Coverage amounts and bare whole-dollar figures are checked only for units: a liability limit written in plain dollars fails.
discloses_rated, rated_not_headlineState the rated limits beside a price for different coverage, and never lead with it as the best option without saying so.
relays_missing, no_guessed_reason"A carrier never silently vanishes"; relay the carrier's own reason; when Foresee couldn't get a quote, say exactly that and never guess why.
mentions, avoidsScenario-specific: say these are estimates, relay the state note, name what would sharpen the price, no invented discounts or bundle savings, no claim to have confirmed or bought.

Is the grader right?

The rules are patterns, so their verdicts were tested rather than trusted. {{labelled}} recorded checks were labelled by reading the full reply: every check the grader failed, a fixed-seed sample of four passing checks per rule category, and three misses found while auditing.

The labels were made during the build by Claude, the assistant used to build the bench, and have not been re-checked by an independent annotator (results/v3/labels.jsonl). The random sample of 44 passes found no misses; the known misses were found outside it. The grader also has {{rule_tests}} unit tests with hand-written good and bad replies, including every counter-example raised in review.

Documentation observations

The contract checks record {{observations}} consistency observations: places where Foresee's published texts differ from each other or from the live schema, two notes about a single example (cent rounding, monthly vs term), and one comparison with the MCP specification. They are opportunities for automated checks, not pricing defects: none was tested against the live quote tool.

Architecture

snapshot/2026-11-10/MANIFEST.json   sources + sha256 (documents fetched by scripts/fetch_snapshot.py)
  ├─ bench/contract.py   ─► results/contract.json        do the documents agree?
  └─ bench/scenarios.py  ─► prompts ─► bench/claude_cli.py ─► results/v3/answers.jsonl
                             (4 setups)   (subscription, no tools)
                                           bench/rules.py + score.py ─► scores.jsonl, summary.json
                                           bench/validate.py         ─► grader vs hand labels
  • Reproducible. Every reply is stored with the hash of its prompt; a run refuses to mix prompts, and earlier replies are reused only when the hash matches.
  • Safe runner. Claude Code CLI on a subscription login: no tools, MCP servers or settings, an empty directory and no API keys in the environment; the stream must confirm all of that, or the run stops. A weekly-usage line stops new calls.
  • Tests. {{tests}} tests: parser, schema walker, every rule with good and bad replies, runner safety, resume, regression demo. CI fetches Foresee's documents first; if they have changed since the capture, the tests that need the pinned versions skip and say so.

I work from Arcturus, my multi-agent engineering workstation. Its practices shaped this project: plain-file records of every decision, approval before any external action, a subscription-only model runner with no tools, and review by a different provider than the one that wrote the code. This project was built in a Claude Code session with OpenAI Codex as the independent reviewer, not by Arcturus's automated build pipeline.

Review history

  • Codex review 1: NO-GO with 16 findings (lenient checks, two inconsistent scenarios, a runner that didn't fail closed, one unfair observation, which was removed). All addressed with regression tests.
  • Codex review 2: NO-GO; 5 fixed, 11 partly fixed, and two wrong verdicts in recorded replies. All addressed and re-scored.
  • Codex review 3: reproduced every reported number; NO-GO for one new bug (Markdown bold read as arithmetic). Fixed and covered by a test, results unchanged. Not re-reviewed: Codex's allowance was used up.
  • After the expansion to {{scenarios}} scenarios: reviewed by a separate Claude reviewer, not an independent provider. It found a grader regression, a consent check that was unfair to setups without the skill, and several wording issues; all were fixed. No independent final GO is claimed.

Limits

  • No live Foresee quotes; published examples may predate the current server. Results are about assistant replies, not about the accuracy of Foresee's estimates.
  • Claude models only; nothing here speaks for ChatGPT or Gemini.
  • The tool result arrives as text in the prompt, without the presentation field (its text isn't published) or a real MCP client's rendering.
  • "No instructions" is a bare baseline: real MCP clients always receive Foresee's tool description.
  • Pattern rules miss some paraphrases and some subtle errors; known gaps are listed in the repository.
  • Small samples ({{per_condition}} replies per setup); gaps of a few replies are direction, not proof.

What could come next
