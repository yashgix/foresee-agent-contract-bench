Agent Contract BenchDo AI assistants keep what matters in a Foresee quote?

Foresee gives AI assistants rich, structured insurance estimates for auto, home and renters. The assistant then turns them into a few sentences for a person. I built a tool that measures what survives that step, and checks that Foresee's agent-facing documents stay consistent with each other.

Foresee

Insurance shopping built for AI assistants

Foresee is built for personal insurance: auto, home and renters, priced alone or as a bundle. Auto in California is live today. An assistant sends a few facts and gets estimates from the carriers Foresee supports, with the detail needed to explain them, and the reason whenever a carrier can't be priced.

≡

Rich, structured estimates

A monthly estimate per carrier with its range, the cost of each coverage, a price ladder showing how the price changes for each listed limit or deductible (one change at a time), and the assumptions behind it.

⇄

Built for agents

An MCP server (the standard way AI assistants call outside tools) with no account needed, plus detailed instructions that tell assistants how to present the result: what to say, and what never to guess.

✓

Confirmation on carrier sites

With the user's consent, Foresee's agents complete carriers' own quote forms and read back the price the carrier shows.

agents add a layer of compression between the information provider and the user. … Premature compression is the root of all evil.

The question

What survives between the quote and the person?

An assistant has to make a detailed quote easy to understand without dropping the facts that change the decision. Foresee's instructions already say what those are. The question is how reliably assistants follow them, and how much the instructions help.

How it works

Two checks, both offline

1 · Replay and grade

23 consumer questions about Foresee's 4 published example results (17 unchanged, 6 with a clearly labelled fictional carrier added). Each is answered by Claude Haiku and Sonnet under 4 setups: no instructions, Foresee's tool description, and each published version of its skill. Deterministic rules taken from Foresee's own guidance grade every reply.

2 · Contract checks

The tool compares Foresee's live MCP schema, docs and skills with each other, so an inconsistency is caught automatically. Renaming one field in the schema makes the check fail; updating the docs makes it pass again.

How it's checked

Recorded replies are re-scored without any model calls, and the grader's verdicts were compared with hand labels. The runner uses a subscription with every tool off and refuses API keys. 88 tests, and independent review of the grading code by OpenAI Codex (final re-check: GO).

Generally kept

Every check on showing different limits beside a lower price, relaying carriers without a price with their own reason, naming assumptions, state notes and ranges passed in every setup. Foresee's result carries these facts itself, and assistants pass them on.

Still lost sometimes

Saying the prices are estimates (12 of 84 replies where it was checked didn't), and prices worked out from the ladder or line items in ways Foresee says aren't valid.

What helped

The tool description removed the unit errors (12 → 0), though on its own it left more unsupported prices (9) than no instructions (6). With either skill, guessed reasons went to zero and unsupported prices to 3 and 3.

Where this could go

Ideas I'd explore next

Each one builds on what the bench already does, and most need only a small change to run inside Foresee's own workflow.

Check every skill edit

Foresee's public repository shows its quote skill revised four times between 29 Oct and 1 Nov. Running the replay on each change would show, per rule, whether an edit changed how assistants present results, before it ships.

Keep the contract in sync

The contract checks can run in CI against the live schema, docs and skills, so a change to one is caught before the others drift. Generating the docs' field tables from the schema would prevent the field-name observations at the source.

Calibrate estimates against confirmations

With confirmed carrier prices from live walks: error per carrier, how often the confirmed price falls inside the range, and an alert when a carrier's filed rates change.

Say "estimate" in the result itself

Replies often didn't say the prices are estimates (12 of the 84 checked). A short line written to be relayed, in the result's presentation text, would put it where assistants reliably look, if it isn't there already.

Test every assistant Foresee serves

The same scenarios can run against ChatGPT, Gemini, Grok and others, so instructions can be tuned for the assistants that matter most to Foresee's users.

Home and renters as they go live

The bench already includes Foresee's home and renters examples. As those lines launch, their scenarios can grow with them: dwelling assumptions, contents limits, bundles.

Technical details

Method, data, results and limits

Everything here is reproducible from the repository: make snapshot fetches Foresee's public documents and checks them against pinned hashes, make check runs the tests, and make score re-scores the 276 recorded replies without a model call.

Data and provenance

EvidenceCountWhat it is
Live Foresee quotes0Not collected. Foresee's terms allow quotes only with your own information, on behalf of a person actually shopping, and don't allow republishing quote data. Test profiles or the author's details would not meet that, so live testing waits for Foresee's permission.
Published Foresee results4The auto, home, renters and auto + renters examples in Foresee's public docs: real outputs Foresee published, not insurer-confirmed prices.
Scenarios on unchanged published results17Different consumer questions about the same published results.
Scenarios with a synthetic change6A published result plus one labelled change: fictional carriers (priced ones marked "(synthetic)"), a state note, or a different coverage ask with the real carriers removed. No invented price is attributed to a real carrier.
Recorded replies27623 scenarios × 4 setups × 3 replies (Haiku twice, Sonnet once). Repeats of one result are not extra data diversity.
Checks scored714Each scenario applies only the rules relevant to it (10 scenario categories).

Tested against the live system: one standard MCP handshake (initialize and tools/list) to read the schema, and public document fetches. Not tested: live quotes, carrier confirmations, latency, load or security.

Setups and rules

The same prompt is sent four ways: no instructions (no Foresee text, a bare baseline), tool description (Foresee's server instructions and tool description, as every MCP client receives them), and with each published copy of the quote-insurance 0.8.6 skill: the website copy and the repository copy, which differ by 35 lines. The tool result is given as text in the prompt, rebuilt from the published dense text and validated against Foresee's live output schema.

RuleForesee guidance it encodes
numbers_supported"State only numbers the result contains — never interpolate." A $ figure written as a price (with cents, or per month, 6 months or year) must match a price, range bound, single ladder step, coverage cost, spread or multi-line total, for the named carrier and stated period. Coverage amounts and bare whole-dollar figures are checked only for units: a liability limit written in plain dollars fails.
discloses_rated, rated_not_headlineState the rated limits beside a price for different coverage, and never lead with it as the best option without saying so.
relays_missing, no_guessed_reason"A carrier never silently vanishes"; relay the carrier's own reason; when Foresee couldn't get a quote, say exactly that and never guess why.
mentions, avoidsScenario-specific: say these are estimates, relay the state note, name what would sharpen the price, no invented discounts or bundle savings, no claim to have confirmed or bought.

Is the grader right?

The rules are patterns, so their verdicts were tested rather than trusted. 94 recorded checks were labelled by reading the full reply: every check the grader failed, a fixed-seed sample of four passing checks per rule category, and three misses found while auditing.

The labels were reviewed during development by reading each full reply; they were not annotated by an independent evaluator (results/v3/labels.jsonl). Documentation observations

The contract checks record 10 consistency observations: places where Foresee's published texts differ from each other or from the live schema, two notes about a single example (cent rounding, monthly vs term), and one comparison with the MCP specification. They are opportunities for automated checks, not pricing defects: none was tested against the live quote tool.

  1. auto.drivers[].age_first_licensed is named in Foresee's guidance but not in the live input schema. The live schema says a key it doesn't name is carried but never rated.
  2. auto.drivers[].years_licensed is named in Foresee's guidance but not in the live input schema. The live schema says a key it doesn't name is carried but never rated.
  3. property.protection_class is named in Foresee's guidance but not in the live input schema. The live schema says a key it doesn't name is carried but never rated.
  4. Per-coverage lines differ from the monthly price by a cent. Likely per-line rounding; agents that add the L rows will not match the headline price.
  5. Website and repository skills are both version 0.8.6 but differ. 35 lines differ; installed copies can't tell which text they have.
  6. The agent-skills index publishes the website skill's digest, not the repository's. Agents that verify the digest get the website text, which lacks rules present in the repository copy.
  7. Docs and live tool describe omitted optional coverages differently. The docs say only the options passed are priced; the live tool description says an omitted um/medpay keeps each carrier's own default. In the docs' own auto example, Mercury's lines include MEDPAY and Travelers' don't, though the request named neither. A comparison can then mix coverages. The repository skill now sends medpay 5000 in its starting point, which narrows this.
  8. Estimates are monthly; confirmations print a term premium. quote_insurance returns monthly prices and accepts a term of 6 or 12 months; live confirmations return the carrier page's own term premium. How the monthly figure relates to a term (and to paying in full) isn't stated, so an agent comparing an estimate with a confirmation has to convert on its own.
  9. live_carrier_quotes progress field is named two ways in the docs. The response table names eta_seconds_remaining; the in-progress example returns eta_seconds. A client written from the table would miss the value.
  10. Priced results use structuredContent only, leaving the text channel empty. MCP 2025-06-18 says a tool returning structured content SHOULD also return the serialized JSON in a text block. Clients that read only text (Foresee runs a separate Cursor host for this) see nothing.

Regression demo

make regression-demo copies the snapshot, renames auto.vehicles[].garaging_zip in the live schema (as a server change would), and runs the checks: one new finding, path-auto.vehicles[].garaging_zip. Renaming it in the docs too clears it. A test asserts both.

Architecture

snapshot/2026-11-10/MANIFEST.json   sources + sha256 (documents fetched by scripts/fetch_snapshot.py)
  ├─ bench/contract.py   ─► results/contract.json        do the documents agree?
  └─ bench/scenarios.py  ─► prompts ─► bench/claude_cli.py ─► results/v3/answers.jsonl
                             (4 setups)   (subscription, no tools)
                                           bench/rules.py + score.py ─► scores.jsonl, summary.json
                                           bench/validate.py         ─► grader vs hand labels
  • Reproducible. Every reply is stored with the hash of its prompt; a run refuses to mix prompts, and earlier replies are reused only when the hash matches.
  • Safe runner. Claude Code CLI on a subscription login: no tools, MCP servers or settings, an empty directory and no API keys in the environment; the stream must confirm all of that, or the run stops. A weekly-usage line stops new calls.
  • Tests. 88 tests: parser, schema walker, every rule with good and bad replies, runner safety, resume, regression demo. CI fetches Foresee's documents first; if they have changed since the capture, the tests that need the pinned versions skip and say so.

Engineering approach

ResearchForesee's docs, live schema and public repository, four competitors, Felix's writing.
Choose the problemFaithful presentation, over estimate calibration, which needs Foresee's data.
BuildA small Python tool: offline, deterministic, reproducible.
Evaluate276 replies across 4 setups; every failure read.
Review and improveIndependent reviews, regression tests for each finding, re-scoring.

Developed with AI coding assistants, following the practices of Arcturus, my multi-agent engineering workstation: every decision recorded in plain files, approval before any external action, a model runner with no tools, and code review by a different provider than the one that wrote it.

Review history

  • Codex review rounds 1 to 3 found real issues: checks that were too lenient, two internally inconsistent scenarios, a runner that didn't fail closed, one observation that was unfair to Foresee (removed), and later a bug where Markdown bold read as arithmetic. Each was fixed with a regression test and the results re-scored.
  • Final Codex re-check: GO. It confirmed the last bug fixed and found no must-fix issues in the grading code (bench/). The site, scenarios and results were not part of that check.
  • The expansion to 23 scenarios and this site had a separate review; its findings (a grader regression, a consent check that was unfair to setups without the skill, wording) were fixed.

Limits

  • No live Foresee quotes; published examples may predate the current server. Results are about assistant replies, not about the accuracy of Foresee's estimates.
  • Claude models only; nothing here speaks for ChatGPT or Gemini.
  • The tool result arrives as text in the prompt, without the presentation field (its text isn't published) or a real MCP client's rendering.
  • "No instructions" is a bare baseline: real MCP clients always receive Foresee's tool description.
  • Pattern rules miss some paraphrases and some subtle errors; known gaps are listed in the repository.
  • Small samples (69 replies per setup); gaps of a few replies are direction, not proof.
